这次究竟解决了什么

从调参，到平台排障，再回到负载本身。

这是一套家用服务器上的 Strata 部署与排障记录。起点是“双路 EPYC、双张 22GB 显卡，为什么生成速度仍然不理想”；随后发现异常低的内存带宽，经历固件设置、分组换条、跨平台测试、换 CPU，最终通过补齐四路电源恢复性能。平台恢复后，我们重新测试 worker、NUMA、PCIe、模型与预填充分块，发现继续堆 CPU 线程已不是有效的提速手段。

一路上我们实际做过什么

10/13

先把速度测准

建立约 20K 输入的固定请求；23→15→23 与 15→7→31→15 worker；补绑核对照。CPU 更多不一定更快。

BF16/SIMT、stage trim、双并发调度、GPU 视觉、视觉预算与显存回收；切 Swift IQ3_S + Q8 PLE；开启 hnorm stream。

10/14–15

官方性能脚本、五组参数、32K–近 256K 长曲线、pipeline2 双客户端；EvalScope 质量评测与 API 同题对照。

10/15–16

确认低带宽不是单一测法

PVE / VM、STREAM / LIKWID、R730 对照、PE / AIDA64；Memory Auto、SOC Pstate、默认 BIOS、DB2 / CB2 分组。

10/16

拆装与业务恢复

R730 借条不兼容，恢复 TrueNAS 与业务；AS4124 重排 GPU 直通；2070S 独立视觉；SC117 质量验收。

10/17及之后

软件更快，硬件异常仍在

部署 0.1.45；长文 prefill 改善，但 PVE 仍约 14 GB/s。随后同批 RDIMM 在 T630 读到约 124 GB/s。

10/18前后

低成本采购与待验证方案

讨论 7302、7352、7402、7452、7443 等；最终一无锁一锁版 7452 共 830 元。安装、PSB 和平台挑 CPU 的说法均保留验证边界。

10/19

找到供电触发条件

换 CPU 后仍低速；补齐四路电源后 AIDA64 约 148 GB/s，PVE 约 141 GB/s。正式开始正常平台上的线程与 NUMA 测试。

10/19后续

收敛到 GPU / MTP / 分块

36 项线程、48 项 NUMA、两模型 PCIe 采样、六组 prefill cap；保留 Huihui / 8192；单独整理 MCE 和 AER。

这个过程没有一开始就沿着正确答案前进。每一步的价值，是让下一步少猜一点：宿主也慢，削弱“仅虚拟化”；PE 也慢，削弱“仅 Linux 测法”；纯 DB2 / CB2 都慢，削弱“只因混插”；T630 正常，削弱“内存条普遍损坏”；换 CPU 不变，继续把注意力转到平台；同配置补齐电源立即恢复，才拿到最强的触发条件证据。

读图之前：哪些数能比较

性能、质量、功能验收是三条不同的证据链。

口径这里的含义最容易误读的地方

后期速度筛查采用 EvalScope Perf 或逐请求采样脚本：单并发、从短到长，简单/复杂各一项；重启加载后先预热；核对模型、参数、实际输入输出 token、前缀复用、MTP、显存与服务恢复状态。worker/NUMA 扫测覆盖 4K、32K、64K、128K、192K、240K；PCIe/模型/cap 使用 4K、32K、128K、240K。速度请求关闭思考，质量评测单独采用较大思考预算。

大部分 10/19 的每个测项只跑一次。图中“六档中位数”是六种输入长度的概括，不是同一项重复六次的置信估计。早期 ABA、三次重复与后期一次筛查分别标注；不把 1%–3% 小差值写成可靠的硬件优势。

全文图表纵轴均从零开始，折线的横轴为测试档位（相邻档位间距相同，不代表 token 间距相同）。完整值可展开；折线只连实测点，没有补造中间值。旧模型、不同生成任务和不同版本之间只作历史参照，不串成一条“累计提速”曲线。

FIELD NOTES / 04

低带宽排查：先排测法，再排内存组

不是看到 2933 / 3200 标签就能认定带宽正常。

首轮自写顺序读取发现 PVE 本地约 8 GB/s、双路约 14 GB/s；来宾默认约 7.9 GB/s。为避免误把程序实现或虚拟化当根因，又改用标准 STREAM 与独立 LIKWID 汇编读取内核，统一工具版本、绑定物理核心和本地 first-touch，加入 R730 对照。结果仍低。[S01]

再进入 PE，避开 PVE 和 VM：AIDA64 两次读取 17.327 / 17.239 GB/s。把 Memory Clock 从手动 3200 改 Auto 后，读数为 17.257；APBDIS=1 / SOC P0 后两次均值 17.1875；恢复 Optimized Defaults 后 17.233。频率和电源策略选项有变化，低吞吐没有恢复。[S02][S04]

用户起初以为八条型号一致，后经 SPD 与实体标签发现是 Samsung M393A4K40DB2-CVF / CB2-CVF，各四条。于是编号，先少条开机，再在相同槽位互换纯 DB2 与纯 CB2。两种四条组读取几乎相同，相差约 0.25%；不能再把“混插”作为足以解释数量级差距的答案。Scrub 关闭对照约 10.098 GB/s，也未恢复。[S03]

MCLK、UCLK、FCLK 不能混用。A 轮曾出现 AIDA64 推算外频与 HWiNFO 成比例矛盾，后续未再出现；没有按比例“校正”带宽。UCLK 读数偏低当时只是线索，隐藏菜单导出也只是可见选项清单，不证明设置已执行或生效。

两次有价值的交叉验证

R730 借出的实际是 LRDIMM，AS4124 本次装上不开机，没有得到有效带宽结果。这是一次兼容失败，不能据此判 AS4124 原 RDIMM 损坏。维护时先检查 N5105 和仲裁，正常关停业务，TrueNAS 最后下线；恢复时先确认存储池健康、TrueNAS 运行，再等至少 5 分钟恢复依赖服务。[S05]

用户后来把 AS4124 原来的同一批八条 RDIMM 装到家中 T630，读到 123.43 / 124.20 GB/s，写入 104.80 / 104.78，复制 112.20 / 111.75。用户补图确认 CB2、DB2 都在场。这显著削弱“这批内存本身只能跑十几 GB/s”的解释，但仍不能仅凭 Intel 平台成绩排除 AMD 平台专属训练或兼容问题。聊天截图转录

R730 恢复业务后再测，双路仅约 15.20 GB/s；页面样本落在两节点约 0.69 / 2.38 GB，空闲内存明显不均。这次成绩不能用来宣称拆装使内存退化，也提醒我们：写了 first-touch，并不保证在线环境实际达到理想的节点本地分布。[S06]

FIELD NOTES / 05

关键转折：补齐四路电源

换 CPU 没有改变低带宽；改变供电状态改变了成绩。

10 月 19 日装上双路 7452 后，AIDA64 读取仍约 17 GB/s。用户原先只让 JPW3、JPW4 对应的两路电源上线，补齐 JPW1、JPW2 后性能立刻恢复；反复观察到四路中缺任意一路都会明显降速，重新接齐可在系统运行中恢复。这里最关键的对照是同一双路 7452、同样的内存速率标注，只改变电源可用状态。[S07]

“电源可用状态触发平台限速”是已复现的解释方向；保护信号究竟由 BMC、CPLD 还是 CPU 哪条路径执行，目前没有完成机制级确认。曾参考过超微其他平台的电源限速资料，但没有把其他型号的 SMART Power 开关直接套到 AS4124，也没有通过关闭保护来解决。0 MB/s 是那次测量异常，不能理解为机器的 DRAM 物理吞吐真的变成零。

复现现象不等于操作建议。应区分支持热插拔的 PSU / 交流输入与主板 JPW 直流连接器；本文不建议带电插拔主板连接器，也无需再主动拔电源复现。

Linux 宿主独立确认恢复

这轮 36 个进程完成，STREAM 数值校验通过；宿主其他 VM 保持运行。单路约 62–73 GB/s、双路约 123–141 GB/s，与 PE 的 148 GB/s 处在同一量级。全供电状态下的旧 7282 尚未复测，因此没有“7452 比 7282 快多少”的干净答案。

八通道、16 个插槽，与当前四条/颗的关系

主板每颗 CPU 有 8 通道，每通道 2 插槽，所以是 16 槽/颗。当前 4 条/颗只占 4 通道；均匀增至 8 条/颗才填满 8 通道；再增至 16 条/颗增加容量和 Rank，不增加通道数，还可能改变可用速率。2Rx4 / 2Rx8 是颗粒宽度，不是内存通道数。

7452 在四通道 3200 下的裸接口算式为 4×3200×8=102.4 GB/s/颗；这是理论值，不是软件保证。7282 官方条目为每插槽 85.3 GB/s、四通道优化，但它仍有 8 个物理通道。不能把它简化成“只有四通道”，或直接用满配 7452 的 204.8 GB/s 预测当前四条配置收益。

FIELD NOTES / 06

早期引擎调优：哪些尝试确实留下了价值

这一阶段仍处于异常供电背景，结论只在各自对照内成立。

最早先用固定请求记录后端速度、缓存命中、MTP 和首字延迟，再做 worker 对照。后来统一真实材料与问题，避免更换提示词让线程数、模型路由和输出长度一起变化。

15 workers 绑核到 GPU 本地 socket 后，decode 中位数 45.0→44.5 tok/s，未见提速，测试后恢复调度范围。这个结果当时只回答一种绑法；恢复正常供电后，后来又做了完整 NUMA 复测。[S12]

初次 BF16 / SIMT 四组合采用 auto，分层也变化，存在混杂；固定分层复核后保留 BF16，未仅凭短测就采用 SELECT_SIMT。SM75 并无原生 BF16 Tensor Core，此处是引擎的转换计算路径，不能理解为开启了硬件原生 BF16 或 TF32。[S14]

尝试观测最终怎样理解
Stage trim释放约4.3GiB，串行速度有明显信号保留；容量收益证据比精确速度百分比更强
hnorm stream + 预留550/600MiB约20K测试：decode61.3，prefill1248，TTFT15.78s多项同时变化，没有 hnorm 单独 A/B
预留进一步回收最低显存余量曾只有约80–134MiB短测没OOM，不等于所有上下文和视觉都安全
Q8 PLE单独加载外置查表权重不是全模型 Q8；没有单变量证明它恢复多少能力
route-prior查到选项，讨论过路由偏置未启用、未做本机收益/质量对照

hnorm 阶段的旧值 49.2 与新值 61.3 不能直接当作独立 +24.6%：输出上限、预热、预留等条件也变了。[S16][S10]

预填充、并发与流水线：收益依赖调度形态

“并发两路”“两组调度”“两段流水”不是同一个参数。

最早保持 parallel=2，只改变客户端串行/并发：端到端总吞吐 34.43→35.98 tok/s，单请求 decode 38.35→23.45，TTFT 1.78→21.14s。总吞吐增幅小且两轮方向相反，没有支持直接上四并发。[S20]

之后跑官方脚本矩阵：ring384、prefill16K、aux-auto、三项一起。大 chunk 在16K prompt 上反而变慢，三项组合也没有叠加收益。aux 对 prefill 有小收益，但 Agent decode 与并发并不同时改善。固定4096另做过单次测试；这个旧版本 auto:4096 实际不会把默认上限降到4096，因此真正测试用的是 --prefill 4096。[S17][S21]

PCIe 到底是不是瓶颈？看阶段，再看接受率

不再把“PCIe专家占比”当作链路利用率。

两张推理卡实际链路均为PCIe3.0×16。逐卡dmon每秒采集RX/TX，引擎每0.25秒采集状态；按prefill与decode分段。同一秒先求双卡合计，再算分位数。双卡单向理论约31.5GB/s；双卡双向理论约63GB/s。只用这些理论分母也不能证明两卡实际共享路径必然能持续跑满。[S38]

因此，当前证据不支持“后面所有瓶颈都在PCIe”。SC117专家命中率98.8%–99.2%，PCIe专家来源仅0–0.1%；decode阶段没有持续带宽饱和迹象。prefill则同时看到GPU高利用率与PCIe突发，未用GPU trace精确拆开计算、搬运和等待。

统计修正也属于这次历程：最初曾相加两卡各自p90，后来发现峰值可能不同步，已按时间对齐重算。本文只用修正后的数值；不再传播旧版“p90相加”的表。不同方向的容量也必须配对：RX对单向31.5，RX+TX对双向63。

最后模型验证中的pcie_frac=0.36（运行时结果，不是通用推荐值）

另保留hnorm stream、aux-cpus auto等原有配置；完整可执行参数以模型JSON为准。Huihui的三个dense分片映射必须一起保留。SC117配置仍在，prefill恢复auto；没有因为这次整理再次切模型。[S44]

resctrl：发现功能，与测过带宽控制是两回事

讨论过用resctrl/MBA限制带宽，以寻找和网友平台相近的条件。10/19的7452内核归档明确出现“resctrl: L3 allocation detected”“MB allocation detected”“L3 monitoring detected”；这是系统检测到资源控制能力的证据，但本轮没有产出经校准的MBA限速扫测成绩，也不能直接把设置值当成实际GB/s。[S45]

尚未完成的验证

  • 全供电状态下重测旧7282，分开供电恢复与CPU型号收益。
  • CPU交换位置或更换后的长期稳定性；受影响核心的独立压力测试。
  • 7443本机实测，频率/IPC/L3的受控比较；resctrl限带宽或其他带宽扫描未产生成绩。
  • 第3张推理卡、修复备用2080Ti、PCIe代际或链路宽度的受控A/B。
  • ROUTE_PRIOR的速度与质量联合对照；Q8与其他PLE单变量质量测试。
  • 当前0.1.45＋Huihui的完整长期质量回归；早期40题BFCL并非这套最终参数的回归验收。
对其他读者最可复用的顺序：先核对平台供电和有效频率 → 用独立工具复核宿主带宽 → 同槽换组或跨平台验证 → 在正常平台上固定请求测线程与NUMA → 分阶段采集GPU/PCIe/MTP → 最后才决定买什么。
