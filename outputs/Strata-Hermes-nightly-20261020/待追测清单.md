# Strata / Hermes 夜间测试待追测清单

记录时间：2026-10-20。来源：对 0.1.45 源码、引擎日志和夜间原始结果的复核。

## 为什么这些项需要追测

- 冷请求微测使用 4K/32K 输入、512 token 输出，多数参数组只跑一次。
- 同一份基准配置两次启动，decode 相差 17% 左右，prefill 相差 7% 左右。
- 单次微测无法分辨小于 10% 的收益，也无法把参数效果与启动状态分开。
- 12 道 Agent 题每题只跑一次，且题目中途修订；它适合做回归，不适合给小差异排序。

因此以下三项保留为"未定论"，不据此启用或否决功能。

## 1. MTP 布局

已确认的事实：

- CUDA 构建的默认是草稿层在最后一级（双卡时即后卡），与流水窗口共用该卡。
- `STRATA_MTP_STAGE0=1` 才是把草稿层移到前卡；`=0` 只是把默认值显式写出。
- 旧报告把 L2 写成"与默认相同"不准确，应改为"移到前卡"。
- `STRATA_SPLIT_MTP_BATCH=1` 的两次运行都没有出现引擎的生效确认行
  （`draft layer prompt K/V batched on CUDA…` 或 `declined`），不能归因。

追测设计：

- 输入：32K 与 128K 两档，使用固定正文。
- 输出：至少 2048 token，最好再加一档 4096 token，让 decode 权重足够大。
- 对照组：默认后卡、前卡（`MTP_STAGE0=1`）、默认后卡加 split batch。
- 每组至少三次独立启动，组间交替，记录启动日志确认草稿层实际位置与 batch 路径。
- 同时记录 `drafts_offered`、`drafts_accepted` 和按深度的接受率。

## 2. prefill-pipe

已确认的事实：

- `R` 是 b/a 的 token 当量：b 为每块的固定专家开销，a 为每 token 开销；该值随机器变化。
- 官方文档记录：填错 R 在同级平台上慢 19% 到 36%。
- 夜间使用的 1536 与 6144 没有在本机校准。
- 1536 组的 4K 简单请求（prefill 631、decode 58.9、接受率仍为 97.5%）与其他三格不一致，
  更像一次运行异常；汇总中位数被它拉低，不能据此判定该功能无效。

追测设计：

- 先做校准：2K 与 8K 固定文本，分别测关闭、均分（1）、768、1536、3072、6144。
- 每组三轮配对，只有稳定快过 3% 才保留；校准文本与正式测量文本分开，避免前缀复用。
- 再在 32K 与 128K 上验证校准值，记录引擎的 `strata prefill: … 在 N-token chunks` 行确认块几何。

## 3. spec-min-p

已确认的事实：

- 该门槛控制"是否再往后猜一个"，不是直接判定草稿对错。
- 短输出下 0.30、0.50、0.70 的复杂任务 decode 基本持平（约 44–49 与 59–61），
  提出数与接受率的取舍互相抵消。
- 简单任务接受率约 97–98.5%，三个门槛几乎没有调节空间。

追测设计：

- 输出 2048–4096 token，让每步验证开销累积。
- 开启 `STRATA_SPEC_DEPTH=1`，记录按草稿深度的接受率，按曲线选择门槛，避免盲扫。
- 每组三次独立启动并交替，重点看结构化输出（JSON、代码、日志分析）这类中间可预测性任务。

## 报告待修正

- L0 应描述为"显式后卡（即默认）"，L2 应描述为"移到前卡"。
- 给 L0/L1 标"变慢"的措辞过强：同布局两次运行本身可差 17%。
- prefill-pipe 1536 的汇总中位数受单个异常请求影响，应加注。

## 4. 引擎速度与任务完成速度的关系

这是 2026-10-20 复核时补充的一条结论，优先级高于前面三个参数项。

观察到的事实：

- 一项 Agent 任务的墙钟时间由模型读取、生成、工具执行、客户端与调度、以及路径长度共同决定。
- 同一模型、同一引擎配置下，12 道题里仅因工具调用次数不同就出现了约 18% 到 32% 的单题耗时摆动
  （T3 的 A 组为 7 次对 3 次工具调用，T6 的 A 组为 9 次对 7 次）。
- 同一批题里，缓存与原始配置的净差异只有 1.6%。

推论：

- tok/s 的提升只有在"模型生成时间占任务时间较大、且解题路径基本不变"时，才容易传导为任务变快。
- 短任务、工具调用多、重试多的任务，会把几个百分点的引擎收益淹没在路径差异里。
- 社区评测偏爱 tok/s，一部分原因是它容易测、容易比较；任务正确率与完成时间难量化，于是被忽略。

质量风险：

- 影响草稿窗口、采样或数值路径的参数（`spec-min-p`、`STRATA_SPLIT_MTP_BATCH` 的 K/V 路径、
  `prefill-pipe` 的专家集合等）可能改变输出位或解题路径。
- 官方文档明确提示，prefill-pipe 的输出位会随卡上专家集合变化，除非使用 `--adapt-swaps 0`。
- 因此这类参数不能只比速度，必须同时跑正确性回归；速度收益小于任务噪声底时，不值得冒质量风险。

建议的追测设计：

- 固定任务与工具序列，或在每次运行中记录完整工具调用序列，便于把路径差异单独列出。
- 分层记录 prefill、decode、工具执行和客户端开销，算出模型时间在任务总时间中的占比。
- 用长输出任务放大 decode 权重，用长输入任务放大 prefill 权重，分别观察。
- 同一任务多次重复，先建立噪声底，再判断小收益是否可辨。
- 决策规则：先看"模型时间占比"，再决定是否值得为几个百分点的 tok/s 调整参数。

## 5. 功耗中间档 220W

已确认的事实（32K 复杂请求，512 token 输出，各三次交错）：

- 250W：整请求中位 23.84 秒，GPU 能量 9913 J，组内最高 81°C。
- 180W：整请求中位 25.81 秒（慢 8.25%），GPU 能量 8618 J（低 13.1%），最高 75°C。
- 分阶段看，180W 的预填充慢 9.2%，生成只慢 4.7%；这个请求约三分之二的时间花在读题上。

追测设计：

- 补测 220W，目标是用尽量小的延迟损失换到大部分能耗收益（期望延迟损失在 3% 到 5% 之间）。
- 至少两种请求：32K 复杂输入（预填充权重高）和同一输入配 2048 token 输出（生成权重高）。
- 250W、220W、180W 三档交错，每档至少三轮；记录整请求、prefill、decode、GPU 能量和最高温度。
- 结论按用途分开写：长材料问答适合哪一档，长输出 Agent 任务适合哪一档。

## 6. 2026-10-20 会话缓存部署记录

已应用并验证：

- 配置：`--conversation-cache-mib 16384`、`--conversation-cache-slots 16`、
  `--conversation-cache-min-free-mib 4096`、`--conversation-cache-min-tokens 1024`。
- 配置备份：`/opt/strata-data/config/strata-huihui-ud-iq4_xs-q8ple-vision-v0.1.45.json.bak-convcache-20261020-120226`。
- 服务重启后：health ok、loaded true、引擎 0.1.45；`/metrics` 显示缓存 enabled true、budget 16384 MiB、slots 16。
- 切换冒烟（约 1550 token 的两段文本，A→B→A）：
  A1 3.85 秒，无暂存；B1 3.19 秒，暂存 A 约 260.8 MB；
  A2 0.80 秒，恢复并复用 1553/1558 token。
- VM 当前可用内存约 31 GiB；16 GiB 预算留出约 15 GiB，引擎保留 4 GiB 的最低可用内存保护，
  内存紧张时会跳过暂存而不是硬撑。
- 16 槽配 16 GiB 大约能容纳 16 个中等长度会话；128K 会话单份约 2.8 GB，
  放不下时会按最久未用淘汰。少于 1024 token 的短会话不占用槽位。

## 7. 双并发与第三张 2080 Ti

目标场景：一个长任务在后台跑几分钟，期间切到另一个会话问几句，问完再回来看长任务。
两个并发槽位就够，三个以上大概率没有必要。

当前约束：

- 配置为 `"parallel": 1`，没有 batch 槽位；第二个请求在服务器队列里等第一个完整结束。
- `pipeline-windows 2` 是单请求内部的流水线，不是请求并发。
- 两张 2080 Ti 的显存只剩约 461 MiB；第二个槽位的会话状态会从专家缓存里挤地方。
- MTP 已开启；开 batch 槽位时应同时试 `--batch-mtp` 和 `--batch-groups 1`，
  否则批窗口里的投机解码路径会退化。
- 会话缓存解决"离开再回来"的等待，批槽位解决"两个请求撞在一起"的等待，两者要分开测。

测试顺序：

1. 基线（`parallel: 1`）：先单独跑一个长任务（建议 32K 输入、2048 token 输出），记录完成时间；
   再在它开始 10 秒后提交一个短问题，记录短问题的首 token、完成时间和长任务被延后的秒数。
2. 两个并发（`parallel: 2` + `--batch-mtp` + `--batch-groups 1`）：重复同样的两次提交，
   记录每个请求的 tok/s、短问题首 token、长任务总耗时，以及显存、专家槽位和专家缓存的变化。
3. 分别测两种短问题：一个是另一个会话的新问题，一个是长任务自身会话的追问。
4. 补一个最坏情形：长任务还在读 32K/128K 输入时提交短问题，因为预填充 admission 是串行的，
   短问题仍可能要等这段预填充结束。

需要记录：

- `live.queued`、每个请求的 TTFT、总耗时、prefill/decode tok/s。
- 引擎启动日志里的 batch 槽位数、`--batch-mtp` 是否生效、每槽的显存占用。
- 专家缓存从多少槽/MiB 降到多少，以及单请求速度退化多少。

验收建议（先定方向，测完再按实际数据收紧）：

- 短问题能在约 5 秒内开始输出，而不是等长任务几分钟。
- 长任务的总耗时退化不超过 15%。
- 没有显存 OOM、没有 batch 相关的正确性回归。

第三张 2080 Ti 22G（若修好）：

- 先做独立稳定性验收：显存测试、持续负载、温度与降频检查，确认没有再出现花屏、掉卡或 ECC 类错误，
  再接入推理池。三层切分里最慢的一级会决定整体节奏，一张不稳定的卡不值得省。
- 接入方式要分三种比较，不能默认"加卡就更快"：
  1. 三层切分：显存和专家缓存增加，但仍需 `parallel: 2` 才有第二个槽位；多一级流水线可能拖慢单请求。
  2. 专家缓存 helper：给主卡腾显存，但可能关闭流水线窗口，需要重测单请求速度。
  3. 单独跑一个小模型专接短问题：真正隔离，但引入第二个模型和路由。
- 只有在两张卡上的 `parallel: 2` 实测不够用时，才进入第三张卡的比较；
  先测两张卡，能把"并发本身"和"显存不够"这两个因素分开。

## 8. STRATA_SPLIT_RING（旧的 ring384）

确认对象：`STRATA_SPLIT_RING`，不是 KV 环形缓存，也不是 batch 的 slot ring。
它控制层切分时，预填充路径向各卡借用的"专家流式环"有多少槽位；槽位越多，
一个 chunk 内能保留并复用的专家越多，但占用的显存、页锁定内存和借用区也越大。
`0` 回到 pinned-share 规则；不设置时，专家驻留率 ≥75% 用 96 槽，否则用 384 槽。

当前 0.1.45 / Huihui IQ4_XS 的实际启动日志：

```
strata serve: prompt chunk auto: 8192 tokens, a 96-slot ring
strata serve: lend sizing: the prompt path borrows 3305 slots (ring 96 slots at chunk 8192),
3305 of them keep their experts in RAM too
```

旧的 ring384 证据（2026-10-14 至 15，Strata 0.1.43.1，Swift IQ3_S，平台供电异常）：

| 组 | 4K prefill | 16K prefill | Chat decode | 双并发总 tok/s |
|---|---:|---:|---:|---:|
| 基线 | 803 | 1251 | 43.60 | 37.56 |
| `STRATA_SPLIT_RING=384` | 862.2（+7.4%） | 1226.2（−2.0%） | 47.6（+9.2%） | 45.61（+21.4%） |

这组数据当时被明确标为"混合、跨时间、只有三轮"，而且平台供电不齐，预填充正是受影响最大的阶段。
现在平台恢复，模型和引擎也换了，值得按同一口径重测。

重测设计：

- 变体：默认（当前 96）、192、384、768；如果 768 有明确收益再补 1536。
- 输入：4K、16K、32K、128K 固定正文，每次确认 `reused=0`。
- 每组三次独立启动，组间交错；记录 prefill tok/s、TTFT、整请求时间、decode、
  启动日志里的驻留率、`streamed ring N slots`、`borrows N slots`、最低空闲显存和专家缓存大小。
- 另加一个 32K 复杂材料 + 512 token 的 decode 守门，确认没有用 prefill 收益换掉 decode。
- 验收：至少两轮里 prefill 稳定快过 3%，decode 退化不超过 2%，最低空闲显存不低于 512 MiB，
  没有 OOM、掉卡或输出位变化；达不到就保持默认 96 槽。
