在 RTX 3090 上优化 Strata：做了什么，快在哪里，下一步还有多少空间

第一篇：在3090和32GB内存上试用 · 第二篇：专家缓存、CPU与GPU分工

前两篇完成了 Strata 的安装和机制分析。这次继续用同一台 RTX 3090 / 32GB 内存的机器，给 Qwen3.8-Flash-Next IQ2_XS 跑实际对话、代码生成，以及收到错误反馈后的代码修复，看看参数调整能换来多少等待时间的改善。

在 4K 输入样本（4392 token）上，优化前后的平均 TTFT（首 token 延迟）从 9.06 秒降至 3.37 秒，降低约 63%；平均 prefill 吞吐量从 486 token/s 提升至 1316 token/s，达到原来的约 2.7 倍。两项指标均取各配置两次测量的算术平均值。随后补做的 24 次隔离对照表明，长输入的主要收益来自更大的分块及对应的流式搬运；固定 256 时，CPU 分担开关的胜负随轮次变化。

代码任务按 decode 吞吐量统计：充分预热的短代码最高为 149.7 token/s，代码修复任务为 5.2–22.1 token/s。质量方面，前者通过全部功能测试，后者出现了输出截断和边界错误，具体结果见后文。

这些结果让后续方向变得具体：先用分块和线程分工改善当前机器，再围绕内存容量与随机读等待，争取让新任务也稳定地快起来。

分块从 256 增到 2048，先省下长输入的等待

--prefill 设置一次处理的输入 token 数；这里仍然一次只处理一个请求。长输入按块处理，每层把使用同一专家的 token 聚在一起，重复利用已搬入的权重。增大分块，可以让一次权重搬运服务更多 token，也需要更大的激活和搬运缓冲。

1024 token 切换的是哪条路径

在本次单卡 CUDA、默认 CPU 分担策略下，当前块小于 1024 token 时，走路由后按需调度的路径；达到 1024 token 时，进入预先搬运专家的流式路径。判断的是当前块的实际 token 数：--prefill 2048 设置了块大小上限，输入末尾不足 1024-token 的块仍可能走小块路径。这个阈值是该版本的调度设置。阈值与默认条件

当前块的处理 小于 1024 token：先路由，再按需分工 达到 1024 token：预先流式搬运
如何决定搬哪些专家 先取回路由结果，统计每个专家服务多少 token；安排被选中的专家 按层、专家编号，提前列出全部未驻留 GPU 的专家并送入循环缓冲
CPU 算什么 从未驻留 GPU、权重可在主机直接读取的专家中，优先挑选服务 token 较少的候选，交给 ExpertPool 这条路径关闭上述 CPU 专家分担；CPU 继续做搬运提交、数据准备等主机工作
GPU 算什么 显存中的专家，以及其他需要搬入的专家；与 CPU 专家计算重叠 被路由选中的专家均由 GPU 计算，驻留专家直接读取显存，其余从流式缓冲读取
PCIe 上的取舍 CPU 接手的专家省去权重 H2D 搬运，但需要传送输入激活和计算结果 可以提前搬下一批权重、与当前计算重叠；也可能搬到当前块没有选中的专家

小块路径会按路由计数挑选 CPU 候选：一个专家只服务少数 token 时，把整份权重搬到 GPU 的成本可能较高，CPU 可以直接读 RAM 里的权重计算。GPU 同时处理其他专家，最后等 CPU 结果回传后再合并。默认分担比例会依据测量调整，还会比较有、无 CPU 分担的层耗时；因此“小块允许 CPU 分担”不表示每层都固定分给 CPU 相同份额。候选选择与自动判断、CPU 结果回传

大块路径利用的是另一种条件：token 较多时，通常会覆盖更多专家，每份权重也能服务更多计算。源码提前枚举各层未驻留显存的专家，以固定顺序提交到循环缓冲。这样准备权重可以早于该层路由结果，复制下一批权重时，GPU 可以处理当前批次。计算仍按实际路由执行；预搬运范围更大，是换取流水线重叠的成本。流式分支与搬运序列

因此，256→2048 同时改变了每块 token 数、CPU/GPU 专家分工，以及权重搬运的调度方式。下面固定线程和模型，先测 CPU 分担开关，再比较更大的分块。这里的开关只控制 prefill 的专家分担，decode 继续使用自身的 CPU/GPU 策略。

固定 256 时，CPU 分担开关没有稳定的胜出方向。 正序中，自动分担平均 11.95 秒，关闭为 18.29 秒；反序中，自动分担为 14.61 秒，关闭为 13.93 秒。关闭组正序还出现了一次 26.14 秒的长尾。两轮都保留在汇总中。

关闭分担确实减少了 CPU 用量：整个请求的 CPU 累计运行时间，平均从 63.32 CPU 秒降到 22.96 CPU 秒。这个计数相加了全部线程的运行时间，包含 prefill 与 decode；它说明 CPU 忙了多久。应用等待的 TTFT 则受到 GPU 专家计算、权重搬运及两边等待共同影响。

提速主要来自更大的分块和流式搬运

在 CPU 分担统一关闭后，256→1024 的平均 TTFT 从 16.11 秒降到 6.14 秒，减少约 62%；正序、反序都出现改善。这一步同时增大了批量，并从路由后按需搬运切换到预先流式搬运。

继续把 1024 增到 2048，平均 TTFT 从 6.14 秒降到 3.54 秒，再减少约 42%。这两组完整块都使用流式路径，末尾小块的 CPU 分担也统一关闭。更大的批量继续摊薄专家权重搬运和逐块调度的开销；2048 六次测量也集中在 3.40–3.64 秒。

这组结果支持把长输入优化的重点放在 分块大小及其对应的搬运流程。CPU 分担适合根据主机与负载保留自动测量，单独关闭它在本机没有带来稳定提速。256→1024 中批量与流式调度各自占多少，仍需固定块长、只切换流式阈值的额外对照；本轮测得的是这两项合在一起的收益。

本轮逐请求数据和完整复现附件保留正反序、预热、响应、配置、资源采样与五字段评分。

怎样观察 prefill 是否拖慢首字：先核对日志中的 prompt tokens / reused / read，再对齐客户端 TTFT 与引擎 prompt_ms。本轮 2048 组平均 prompt 时间为 3.505 秒、TTFT 为 3.542 秒；256 自动组分别为 13.249 秒和 13.281 秒。首字前的时间主要落在引擎 prompt 阶段。24 次正式请求全量读取输入、实际读盘增量为零，增大分块后这段时间明显缩短，说明当前热输入的 prefill 流程确有优化空间。要把时间继续拆到某个 kernel、复制或 event wait，需要 CUDA 时间线。

给后台线程留 CPU，MTP 保留 4

这台虚拟机有 16 个逻辑 CPU。原配置让 15 个工作线程加主线程共同计算专家。候选配置使用 7 个工作线程加主线程，把其余 CPU 留给后台工作；日志确认 --aux-cpus auto 将相关线程放到了逻辑 CPU 8–15。线程亲和说明

本轮只试了 15 和 7 个 worker，随后采用 7 个 worker 配合 aux-cpus auto 进行确认测试。选择它的目的是让专家计算使用 8 个逻辑 CPU（含主线程），把另外 8 个留给数据准备和其他后台工作。

7-worker 单项筛选的区间合并测到 79.9 token/s。其他线程数量尚未测试，而且现有轮次的页缓存和读盘量有差异，所以目前采用的是这套分工的试用配置，最优 worker 数量尚未确定。确定最优值，需要在相同数据准备条件下比较多个线程数，并分别检查后台绑核的影响。

MTP=8 的两次区间合并分别为 36.9、50.6 token/s，MTP=4 的候选关闭组为 74.1、71.2 token/s，四份代码逐字相同。整组草稿接受率分别为 65.9% 与 73.4%。更长的草稿增加了生成与验证工作，只有被接受的部分才能节省后续轮次；本轮据此保留 MTP=4。

线程分工和 MTP 都会与其他路径相互影响。后台线程需要及时准备数据，主线程需要推进调度，GPU 需要等待相应输入。当前筛选结果支持继续使用这组候选参数，后续在减少存储等待后，可以更清楚地比较它们的计算收益。

怎样观察 CPU 分工是否有效：先用启动日志核对 participating threads、worker/host 的逻辑 CPU 和 strata aux cpus，再比较同题的 CPU 累计时间与请求延迟。本次日志记录 8 个参与计算线程，主线程在 CPU 0、worker 在 1–7，后台线程分配到 8–15。256 分块的开关对照中，CPU 累计时间为 63.32 / 22.96 CPU 秒，TTFT 却未随 CPU 用量降低而稳定改善。分工设置已生效；线程排队、主线程调度和 stager 等待各占多少，仍需逐线程调度记录定位。

怎样观察 MTP 是否划算：同题同时检查 draft_n_accepted / draft_n、decode 用时、输出长度、读盘和验收结果。本次 MTP=4 的确认组累计接受 2974/4052 个草稿 token，MTP=8 为 3304/5012，对应 73.4% / 65.9%（各 16 个正式请求，含代码修复）。结合前面的同输出代码对照，本次加长草稿没有带来速度收益，保留 4。该组包含不同答案与 I/O 状态，数字反映整组运行效果。

kv-grow 为什么没有启用

--kv-grow 让 KV 状态按实际到达的上下文长度占用显存，尚未使用的空间先交给专家缓存；上下文增长时，专家缓存再让出空间。本版本为这条路径设置了一个条件：所有专家在系统内存中都有可用副本，这样 GPU 让出任意专家槽位后，CPU 仍能处理对应专家。

这台 32GB 机器使用 --resident-experts：RAM 主要保留 GPU 没有驻留的专家，以及 prefill 借用区域的备份。它满足当前低内存运行方式，但不满足 kv-grow 的全专家 RAM 条件。源码明确排除了这两种模式的组合，测试日志也输出 --kv-grow is off。所以这项试验实际仍使用原来的 KV 分配方式。启用条件

这一层的观测结论：日志明确给出 --kv-grow is off，本次没有进入动态增长路径。当前看到的是功能启用条件未满足；KV 增长过程的显存压力，需要在满足条件的运行方式下另测。

GPU 和 PCIe 忙在哪里，现有数据能看到什么

这份模型还有约 28.8GB 的 PLE n-gram 表。当前模式在 RAM 中固定了约 16.17GiB 的专家补集，PLE 走 mmap，由操作系统缓存访问过的页。32GB RAM 需要在运行数据与文件缓存之间分配空间。模型数据布局

相关请求的日志记录专家 blob 文件读取为零，而进程仍有实际存储读取；结合 PLE 的 mmap 路径，证据主要指向 PLE 表与文件页缓存。逐文件 I/O 归因是下一步验证内容。

mmap 让访问过的数据页留在系统缓存里。新任务访问其他页时，需要由存储补齐；内存空间也会影响这些页能保留多久。本机 direct 路径的随机读探测约 2MB/s，最终配置保留引擎自动选择的 mmap 路径。对这种零散读取，关键指标包括每次读的等待和同时在途的请求数，顺序读带宽只能描述另一类负载。

怎样观察 RAM 与磁盘是否影响请求：在请求前后读取 /proc/PID/io 的 read_bytes 和 /proc/PID/stat 的 majflt，并用同时间段的 /proc/meminfo 检查可用内存。read_bytes 描述实际存储读取量，major fault 描述需要存储取页的缺页事件；再把它们同耗时关联。

更好的预期：让新任务少读盘，让快的状态维持得更久

当前机器已经展示过两种状态：重复短题解码接近 150 token/s，改变输出内容的修复任务则可能等待几十秒。下一轮最值得争取的改善，是减少新请求的数据等待，让相近任务的完成时间更稳定。

首先把内存预算列出来：

数据 当前规模 放置方式与需求
未驻留显存的专家补集 约 16.17GiB 当前配置固定在 RAM
PLE n-gram 表 约 28.8GB，折合约 26.8GiB 当前走 mmap；全表常驻需要这部分 RAM
上述两项合计 约 43GiB 还需要给系统、服务及其他工作缓冲留空间

这两项合计已超过当前约 31.3GiB 的可见 RAM。下一轮可以把虚拟机内存扩到 64GiB，保持 CPU、GPU、模型和任务不变，比较 mmap 与 PLE 全表常驻。64GiB 是按这份模型和当前模式提出的实验容量，加载成功、实际占用和长输入测试共同决定它是否够用。

如果主要等待确实来自 PLE 的缺页读取，那么全表驻留后，新题访问 PLE 时就能直接从 RAM 取数据。预期先体现在请求期间读盘减少、首字与完整耗时缩短，以及慢请求之间的波动收敛。CPU 专家计算、PCIe 搬运和 GPU 验证仍有各自成本，届时再测它们限制了多少速度。

下一轮对照 保持什么一致 期待看到什么 如何确认
32GiB mmap → 64GiB mmap 模型、参数、CPU/GPU、题集与运行顺序 更多访问过的页可被保留，重复运行更稳定 请求读盘、major fault、首字与完整耗时
64GiB mmap → 64GiB PLE 常驻 同一容量与其他参数 新题的 PLE 访问等待减少 日志确认常驻；逐文件读盘与任务耗时对照
读盘下降后重新比较线程与 PCIe 份额 固定题目、输出验收及数据准备方式 找到当前 CPU/GPU 分工更合适的比例 相同任务重复测量，检查时间与质量
扩充独立代码任务，再测尾部开关 相同代码题、测试集与输出预算 更清楚地判断省下的时间对应怎样的成功率 首次通过率、反馈后通过率、截断数及完成时间

这些是待测预期。本文中的 149.7 token/s 是已测到的热短题峰值，108.8 token/s 是一份通过测试的 505-token 日志代码结果。它们提供了观察计算路径的参照；增加内存能把多少新任务带到相近速度，要由下一轮同题对照给出。

对实际使用，下一轮会把“重复同题”和“第一次运行的新题”分别统计，再给出完成时间的中位数和 p95。这样更容易判断每天发出的请求会等多久。
