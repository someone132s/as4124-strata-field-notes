## 1. 先看结论与证据等级

目前保留的组合是：**15 pool workers、2 个并发槽位、`--batch-groups 1 --batch-mtp`、自动分层、`STRATA_BF16_TC=1`、`STRATA_STAGE_TRIM=1`、256K 上下文**。当前为模型质量评测关闭视觉，显存预留恢复为两卡各 700 MiB，加载 Swift IQ3_S + 外部 Q8 PLE。

这些结论不是同一场测试得出的，也不意味着每个开关都在当前 IQ3 上完成了独立复核。

| 标记 | 含义 | 使用边界 |
|---|---|---|
| 本机实测 | 有本机报告、原始 JSON/CSV 或运行配置 | 只支持相应硬件、版本、模型、负载下的结论 |
| 社区报告 | GitHub 作者、网友文字或截图 | 作为候选；不与本机成绩直接相除计算硬件收益 |
| 推断 | 根据机制与现有数据提出的解释 | 不写成已经查明的瓶颈 |
| 待验证 | 尚未进行本机对照 | 不应混进“已采用且验证有效”的配置 |

本机已有证据支持：worker 存在平台期，特定绑核方案没有收益；BF16 开关对 prefill 的收益较可靠；stage trim 增加专家缓存；本机测试中的单组批量 MTP 调度优于两组流水调度。**尚未证明** CPU IPC、内存带宽或频率分别占多少瓶颈，也没有证明更换某款 CPU 后能达到网友速度。

## 2. 硬件与测量口径

### 2.1 本机平台

| 项目 | 已知配置及边界 |
|---|---|
| 宿主机 | Supermicro AS-4124GS-TNR / H12DSG-O-CPU，PVE |
| CPU | 双 EPYC 7282，共 32 物理核心、64 SMT 线程 |
| 内存 | 宿主机 256 GB，8×32 GB，每个 CPU 4 条；当前插槽记录为各侧 C2/D2/G2/H2 |
| 内存速率 | SMBIOS 显示配置 3200 MT/s；不等于实测带宽或带宽已跑满 |
| 本次使用 GPU | 2×RTX 2080 Ti 22G，单卡报告 22528 MiB，Turing SM75 |
| PCIe / NUMA | 两张卡在 PVE 中均接宿主 socket 0；PCB“CPU1”与系统从 0 编号不冲突 |
| GPU VM | `root@10.2.21.4`，VM502，128 GiB 内存；正式 worker 测试阶段为 36 vCPU |
| 测试 VM | `root@10.2.23.3`，运行 EvalScope，与推理服务分离 |
| 其他 GPU | 2070 Super 等未加入本轮推理；独立视觉卡只是后续设想 |

`pool-workers`、VM vCPU、宿主物理核心和 SMT 线程是四个不同计数。15 workers 通常还涉及 host 主线程，但不能因此把 VM 简化为“只用了 16 个物理核心”。

### 2.2 速度必须带口径

- **后端 prefill**：引擎记录的读入 token / prompt 时间。须同时看真正新读入多少、复用多少。
- **后端 decode tok/s**：输出 token / 引擎 decode 时间；与客户端端到端吞吐不同。
- **TTFT**：客户端到首个有效输出的时间，可能包含排队、读入、思考、调度及网络。
- **并发总吞吐**：同组所有输出 token / 该组从提交到全部完成的墙钟时间。本记录明确写“总吞吐”时采用此类口径。
- **专家命中率**与**MTP 草稿接受率**不是一个指标；高接受率也不代表草稿计算、验证和同步没有成本。
- **峰值、单请求中位数、整批平均、端到端吞吐**不能互换。尤其不能拿网友 200 tok/s 峰值对比本机 20K 输入双并发端到端成绩。

早期 worker 测试有大量前缀复用；后来的 Turing、调度和模型短测中有明确的 `reused=0` 负载。输出上限也从长回答、2048、1024 到 512 不等。因此下文各阶段成绩应在各自阶段内部比较，不能串起来当作同一条性能增长曲线。

## 4. 本机调优过程与结果

### 4.1 接手基线与早期 worker 对照

早期用户观察过 60 vCPU 不如较少 vCPU，但提示词和输出未严格一致，只能作线索。后来先复用社区测试脚本做 23→15→23 对照：三组单请求速度中位数约 46.8、49.9、44.1 tok/s；合并 23-worker 基线的整体 decode 吞吐约 45.77，15-worker 为 46.90 tok/s。15 降低 CPU 占用，但前后基线漂移明显，不能据此宣布固定百分比提升。

随后配置日志保留参数、计数、时间和哈希，不记录私有课本文本及生成正文；使用用户的 `text` 与 `questions` 建立自己的固定负载。预热题为“这段文字的主要内容是什么？”，正式选三个问题，避免更换题目导致路由、输出长度和接受率同时变化。

依据：[workers 详细报告](Strata_workers详细测试报告.md)、[文本脚本说明](Strata文本测试脚本说明.md)、[接手记录](Strata接手记录.md)。

### 4.2 不绑核：15→7→31→15

时间：10-13 21:50–22:45。模型 huihui UD-IQ4_XS，固定 27/21 分层、PCIe fraction 0.28，VM 36 vCPU；每组一次预热、三个问题各三轮，共 36 个正式请求。

| pool workers | 正式样本 | decode 中位数 tok/s | 均值 tok/s | 变异系数 | TTFT 中位数 s |
|---|---:|---:|---:|---:|---:|
| 15（两组汇总） | 18 | 45.0 | 44.5 | 5.4% | 6.38 |
| 7 | 9 | 41.1 | 40.9 | 4.3% | 6.48 |
| 31 | 9 | 43.7 | 41.2 | 12.4% | 6.34 |

为什么测 7/15/31 而不是字面 8/16/32：测试设计考虑 worker 池之外还有主线程，近似覆盖 8/16/32 个参与线程的候选档位；这并不等于一一独占物理核心。

用前后 15-worker 基线插值配对，7-worker 约慢 8.2%，31-worker 约慢 5.4%。首尾 15-worker 中位数自身也从 45.6 到 43.1，漂移约 -5.5%。因此结论是 **15 是当前负载合理的工作点，增加到 31 没有收益且波动更大**，而不是证明“16 物理核心就是所有模型的精确最优值”。

依据：[不绑核正式报告](Strata不绑核workers正式测试报告.md)、[原始汇总](unbound-comparison-20261013-215059.json)。

### 4.3 15 workers 绑核对照

时间：10-13 23:05。将 guest 主线程及 worker 所在的前 16 个 vCPU 映射到 GPU 本地 socket 的宿主物理核心 0–15，其余 vCPU/QEMU 保留可调度范围，完成 9 个正式请求。

| 指标 | 不绑核 15 | 绑核 15 |
|---|---:|---:|
| decode 中位数 tok/s | 45.0 | 44.5 |
| decode 均值 tok/s | 44.5 | 43.6 |
| TTFT 中位数 s | 6.38 | 6.28 |

逐题配对中位变化约 -2.2%，未见提速。测试后恢复所有 36 vCPU 的宿主 affinity 0–63。**本次策略没有收益**；不能扩大为 NUMA、内存放置、所有形式的 CPU 亲和性永远无影响。

依据：[绑核报告](Strata15workers绑核对照报告.md)、[线程映射](bound-w15-20261013-230530-thread-mapping.json)。

### 4.4 初次双并发与 CPU 视觉

10-14 00:14 将服务设为 15 workers、2 槽位、2 groups、256K，上调 CPU 视觉到 16 threads / 8192 token 上限。短请求验证两个槽位可同时活动。专家缓存由约 30628 降到 28506 MiB，槽数 13253→12333，说明并发状态及缓冲区也会吃显存。

用户实际图片出现约 5 分钟超时，00:42 恢复图像上限 1024。这一观察支持 CPU 视觉在大图预算下不适合当前需求；它不是对 GPU 视觉的测量。

正式并发对照保持同一台 parallel=2 服务，只改变客户端串行/双请求同时提交，每组 12 请求：

| 指标 | 客户端串行 | 客户端双并发 |
|---|---:|---:|
| 端到端总吞吐 tok/s | 34.43 | 35.98 |
| 单请求 decode 中位数 tok/s | 38.35 | 23.45 |
| TTFT 中位数 s | 1.78 | 21.14 |
| 请求时延中位数 s | 54.97 | 106.51 |

两轮吞吐变化一轮 +22.07%、一轮 -10.59%，总体 +4.52% 不足以宣称稳定扩展。缓存复用和 MTP 调度差异参与其中，不能把 TTFT 差简单说成固定排队开销。四请求测试验证两槽位排队可完成；`live.running=4` 包含等待请求，不表示四路同时 decode。

决策：保留 **2 并发**满足使用需求，暂不上 4。更多并发的代价包括缓冲区/KV/草稿状态、专家缓存被挤占、单请求速度下降与排队；不能只盯 CPU 利用率。

依据：[两并发配置](Strata两并发配置记录.md)、[并发能力报告](Strata并发能力测试报告.md)。

### 4.5 Turing BF16 与 SIMT

10-14 01:45–02:35，测试 BF16/SIMT 四组合。每组两次预热、三个串行、一个并发对，共 28 请求。首次使用 auto 分层，各组分层发生变化，存在混杂：

| 环境开关 | prefill tok/s | decode 中位数 tok/s |
|---|---:|---:|
| 均关闭 | 922.8 | 43.8 |
| BF16_TC=1 | 1088.5 | 42.7 |
| SELECT_SIMT=1 | 953.1 | 43.3 |
| 两者都开 | 1056.2 | 42.6 |

随后固定 **24/24、PCIe fraction 0.28** 复核 BF16：prefill 929.7→1086.6（+16.9%），TTFT 21.08→18.33 s。decode 中位数 37.2→42.7，但逐题变化 -3.3%、+7.1%、+14.8%，只有三个请求，且首次四组没有同样趋势。

决策：保留 **BF16_TC=1**，最有把握的收益是 prefill 约 17%；不承诺稳定 14.8% decode 提升。没有足够证据采用 SELECT_SIMT。

机制边界：SM75 没有原生 BF16 Tensor Core；此开关走 BF16→FP16 操作数转换与 FP32 累加，可能产生舍入差异。SELECT_SIMT 是另一条评分内核路径，并非“打开 TF32”。详见[官方旧 GPU 说明](https://github.com/Niko1221/Strata/blob/v0.1.43.1/docs/OLDER_GPUS.md)。

依据：[四组测试](Strata_Turing优化测试报告.md)、[固定分层复核](Strata_Turing固定分层复核.md)、[持久开启核验](Strata_BF16开启核验.json)。

### 4.6 Stage trim 与双并发调度

10-14 上午进行固定 24/24、BF16 开启的 A→B→A 测试。

**Stage trim：**专家缓存 28506→32913 MiB（+4407 MiB，约 +15.5%），槽数 12333→14235。三组 decode 中位数分别 41.5→48.8→42.4 tok/s；prefill 1047→1146→1079 tok/s。说明本机释放缓存有实际收益，但每组只有三个串行样本；其并发对照没有完成完整 ABA，不能把所有并发收益也归给 trim。

**调度：**在相同硬件、模型和固定分层下比较两组流水调度与单组批量 MTP，采用同时到达、错峰到达各三对：

| 到达模式 | groups=2，A1 总吞吐 | groups=1 + batch-mtp，B | groups=2，A2 |
|---|---:|---:|---:|
| 同时到达 | 10.94 | 22.19 | 10.85 |
| 错峰到达 | 13.59 | 22.19 | 13.19 |

单位 tok/s；1024 输出上限，约 20K 输入、不复用、关闭思考。B 同时到达整对用时约 92.3 s，A 为 187.2/188.7 s；该负载约 2.04 倍。错峰约 1.66 倍。**它不是所有并发负载翻倍的保证。**

决策：后来按用户授权保留 `STRATA_STAGE_TRIM=1` 与 `--batch-groups 1 --batch-mtp`。实验用固定分层控制变量；日常配置仍按用户要求使用 auto。

脚本曾出现恢复校验误报、错峰触发字段错误；核对真实配置后修正并重跑相关测试。报告中的脚本错误不代表服务最终恢复失败。

依据：[本轮总报告](test-report-2026-10-14.md)、[trim 原始记录](remote-results/stage-trim-aba-20261014-110028.json)、[调度原始记录](remote-results/scheduler-ababa-20261014-120432.json)。

### 4.7 GPU 视觉、token 预算与显存回收

10-14 13:59 起使用 SM75 CUDA 视觉 helper，保留原主引擎，镜像为 `strata:vm502-sm75-vision-gpu`。构建记录中的主引擎 SHA256 为 `fd9bda722a0842a1970e2a8bb19e5c16dbf0b8f385fe9f6cd4f36c98a8353d20`。这次需要补建的是我们镜像里的 GPU 视觉能力，不代表 Strata 的所有发布包都必须重新编译才能支持视觉。

路径依次为：GPU 1024 → 4096 → 16384；同图细节改善是用户主观观察，尚非多模态 benchmark。16384 首次触发显存问题，增加预留后通过，再尝试回收。

| 阶段 | 主卡/后续卡预留 MiB | 图像上限 | 结果 |
|---|---|---:|---|
| GPU 视觉初启 | 700 / 默认后续预留 | 1024 | 功能通过，尚不覆盖大图峰值 |
| 高预算初试 | 低预留 | 16384 | 发生 OOM，不能只看空闲稳态显存 |
| 增加 headroom | 4096 / 700 | 16384 | 4096² 测试图实际 128×128 网格、16384 token，117.73 s，HTTP 200 |
| 回收部分 headroom | 3072 / 700 | 16384 | 同类测试图 118.37 s，采样最低空闲约 778 / 148 MiB，未见 OOM |
| 当前纯文本评测 | 700 / 700 | 关闭视觉 | 恢复更多专家缓存 |

4096→3072 回收对照：缓存 24935→26140 MiB，槽 10798→11318；串行 decode 中位数 33.70→32.90（-2.37%），prefill 971.24→1003.57（+3.33%），并发总吞吐 12.11→12.56（+3.71%）。auto 分层由 19/29→21/27，PCIe fraction 也变动；因此证明的是“该配置通过了这组测试且未明显恶化”，不是“每回收 1 GiB 固定提速多少”。

用户一次十张 3840×2160 图片观察到逐张编码、显存稳态基本不变。此观察有参考价值，但单请求串行图像不会覆盖两请求同时编码、首次 CUDA graph capture、不同网格形状等所有峰值。测试采样的最低空闲显存也可能漏掉瞬时峰值。图像 token 是上限，不保证每张都吃满，更不是固定 1024；应看实际网格/使用量。

目前没有完成单独 2070S 视觉部署或多卡视觉编码实验；“视觉使用哪张卡”应看 helper 的设备选择及实际进程显存，不能仅由模型采用流水并行推导。

依据：[GPU 视觉构建及功能](remote-results/gpu-vision-mtp-20261014-135915.json)、[16384 headroom](remote-results/vision-headroom-20261014-143944.json)、[回收测试](显存回收测试-20261014.md)。

### 4.8 Swift IQ3_S + Q8 PLE 与关闭视觉

10-14 15:54 切换 Swift IQ3_S 主模型，按用户要求直接搭配外部 Q8_0 PLE。两者下载仓库见[模型说明](Swift模型与Q8_PLE说明.md)。

- Swift 与原 huihui 不只是量化档位不同，权重处理、GSQ/RCO、abliteration 等也不同。
- Q8 PLE 是特定查表权重，不是把整个模型变成 Q8；更不能恢复低比特专家丢失的精度。
- 分片编号重叠导致默认扫描冲突时，通过 `--native-dense-gguf` 显式指定 Swift 首片，`--ple-gguf` 单独指定 Q8 表。
- Q8 PLE 文件约 54.40 GB，原低比特表约 28.80 GB，磁盘差约 25.60 GB；磁盘文件总大小不等于运行时 RAM 或显存占用。

| 同阶段短测 | 开 GPU 视觉 16384 | 关视觉纯文本 |
|---|---:|---:|
| 专家缓存 MiB | 27465 | 31913 |
| 专家槽 | 14115 | 16387 |
| 串行 decode 中位数 tok/s | 46.0 | 49.2 |
| 单对并发端到端吞吐 tok/s | 16.20 | 16.31 |

不是严格 A/B；纯文本短测仅三个串行、一个并发对，输出上限 512，temperature=0，reasoning=none，不复用。纯文本三个 decode 值为 45.4/49.2/59.2，prefill 加权约 1211 tok/s，TTFT 中位约 16.37 s。不能把不同阶段的 45、33、49 tok/s 直接解释为视觉开关单一因素造成。

依据：[部署记录](Swift-IQ3S-Q8PLE-deployment.md)、[纯文本短测原始记录](remote-results/iq3-text-only-smoke-20261014-181132.json)。

## 7. 关于硬件升级与模型质量的暂定边界

**CPU：**worker 平台期可以由内存等待、同步、GPU/PCIe 等多种原因产生。主频、IPC可能有用，但没有频率对照或硬件性能计数，不能算出收益。7443、7R13 的核心数与价格讨论是采购候选，不是测试结论；用户当时报价不是当前市场报价。

**内存：**现有每路四条与更多通道填充值得研究，但双路内存不等于对单请求自动合并成双倍带宽。没有完成 STREAM、内存控制器带宽计数或 stall 分类。CPU总占用率不能分解出内存等待比例；单一 cache-miss 数也不能直接换算等待时间。更换 CPU 或 DIMM 方案的收益目前都没有测定。

**热专家与智力：**缓存位置决定哪些权重读自显存、RAM或文件；正常缓存机制不应被描述成“只有显存专家参加投票”。“专家数×量化位数决定模型智力”“IQ3必然达到95% API”均无本机质量证据。量化、不同权重、PLE、采样、路由相关改动、输出截断应分别看待。

**质量评测：**目前按用户授权进行 IQ3→huihui UD-IQ4_XS 两轮，每轮 300 样本：C-Eval80、MMLU-Pro60、IFBench60、BFCLv4 40、GPQA40、LiveCodeBench20。使用统一采样配置、固定种子与配对题目；这些是定性筛选，不用于宣称精确总体排名。长程 agent 能力还需要后续 Hermes 实际任务人工评价，不能由工具调用单项分数完全替代。

正式评测通常请求 reasoning high，max_tokens16384 / budget12288；GPQA及代码项32768 / budget24576，batch2。它与速度短测的 reasoning none、512/1024输出上限不同。正式任务未全部结束前不写模型胜负，也不因本文收集了新参数而中途调整。

评测计划与状态位置：测试VM `/opt/evalscope/configs/campaign-plan.json`、`/opt/evalscope/outputs/campaigns/iq3-vs-udiq4-20261014/status.json`；[评测启动记录](EvalScope两轮评测启动-20261014.md)。
