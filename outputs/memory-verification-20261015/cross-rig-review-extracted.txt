Strata 跨机对比复盘：同为双 2080 Ti，差距为何不对称
日期：2026-10-15 · 口径：引擎内计时（prefill = 读入 token 速率；decode = 纯生成速率）· 全部数字为实
测，未插值、未跨平台归一化
0. 结论速览
decode 的差距，主要来自「模型谱系」与「任务形状」，不是机器故障。 去审查（abliterated）谱系模型
在我们自己的参考机上同样只有 52–60 tok/s——和报告作者机上报告的 55–60 几乎重合。这类模型的草稿
接受率显著更低（66–79% vs 常规权重 98%+），decode 在任何机器上都会明显偏低；连其上游基底
Swift-1.5 本体（参考机全栈实测）也只有生产的 0.8×（见 §2.5）。
prefill 才是真正异常项，且只出现在报告作者那台。 它出现「64K 见顶（1439）后回落到 1153」的倒挂形
状；参考机与 2690v4 网友机都随长度单调上升到 2.4–2.7K。倒挂与模型、与配置均无关（§2.5、§3 排除
法），指向该机的环境：宿主内存数据通路异常为第一嫌疑（同口径实测与参考机差 5.9×，§3.5），VM 直
通链路未复测、显存余量≈0、长上下文 KV 主机侧路径次之。
2690v4 网友机基本正常。 prefill 对参考机恒定落后 1.08–1.10×（正常范围内）；decode 的差距可由「量
化更大（UD-Q4_K_XL ≈1.4× 字节/token）+ 任务接受率 + 无补丁批 + 2016 平台」折算解释，残差仅
~1.1×。

2. 先剥离四项不对等
任务形状：参考机公开数是计数任务（接受率 98%+）；报告作者机/2690v4 机为分析类任务（接受率 72–
79%）。同机换任务，decode 约差 1.2–1.3×。
量化等级：2690v4 用 UD-Q4_K_XL（≈4.5 bpw，≈1.4× 字节/token）；其余为 IQ3_S（≈3 bpw 级）。
补丁与环境变量：参考机带 sm_75 批次补丁（9 个上游未合并 PR，实测 +6–11%）+ 五枚调优环境变量；两
位网友均无（且报告作者机是否开全环境变量未核验）。
模型谱系（最关键）：报告作者机用的是 Swift-1.5-abliterated（去审查）权重。参考机在 2026-10-10 曾完
整跑过同谱系的去审查版（SC117 的去审查 IQ3_S）：三点 decode 51.7–60.1，接受率 66–74%，prefill
1718→2399（形状正常）——与报告作者机的 55–60 几乎重合。 → 同一台已知正常的机器，换上去审查谱
系，decode 立刻掉到 55–60 档。 因此报告作者机的 decode「低」，主要是模型与任务的属性，不是它的
机器坏了。
2.1 decode 差距的量化折算（先前评估的完整账）
以参考机生产栈（前述三点 decode ≈ 149–157，计数任务、接受率 98%+）为被除对象，逐项折算两位网友的
decode：
2690v4 机：÷1.35（UD-Q4_K_XL，≈1.4× 字节/token）÷1.24（任务形状，接受率 ~79%）÷1.08（无
批次补丁）→ 预期 ≈ 80–82；实测 72.5 → 残差仅 ≈1.1×（2016 年平台），解释干净。
报告作者机：×0.8（Swift-1.5 配方本体代价，§2.5 参考机全栈实测）× ≈0.55（去审查衍生再折，由
SC117 试点 52–60 与谱系观测夹定）→ 预期 ≈ 66；实测 55–60（其任务接受率更低 72–79%）→ 机器残差
≈1.0–1.2×，几乎无额外惩罚。
机制备注：本引擎 decode 与「草稿接受率 × 单步时间」成正比，且 per-token 走串行主机路径（部署指南附
录 B 原文：decode 受主机侧专家流带宽约束）；但本案例的跨机差距主要落在「单步时间/模型谱系」项上，
主机侧只在报告作者机的 prefill 形状上留下独立痕迹（§3.5）。

两条硬结论： 1. 在正确配置下，Swift-1.5 的 prefill 与生产 IQ3_S 无差（8K 以上逐点 ≤2%，230K 仅差
0.1%）——「Swift 把 prefill 拉低」不成立。此前一次同模型的低值+倒挂（1663→1734→1534）出现在官方
默认配置下（无批次 env、无 pw2、--prefill auto、spec-min-p 0.5）；换回生产参数后曲线立即恢复单调
上升。给社区的一条教训：长端 prefill 掉速先核对 pw2 / auto:16384 / 批次 env，再怀疑机器。 2. Swift-1.5 自
身的代价集中在 decode ≈ 0.75–0.9×（中位 ~0.8×），且不是接受率造成的（其计数任务接受率 92–96%，接
近生产的 98%+；单步时间才是主因——重训权重改变了专家路由）。
3. prefill 倒挂的定位（报告作者机仍是唯一异常）
排除法： - 不是 CPU/内存的「档次」：2690v4 机的 CPU/内存远弱于双 EPYC 7282 宿主，但它的 prefill 只恒定
差 1.08–1.10×、形状正常。（「档次」不背锅 ≠ 内存无罪——同一台报告作者机的宿主内存通路本身存在结构
性故障，见 §3.5。） - 不是模型：参考机用全栈配置实测 Swift-1.5，prefill 与生产同款（见 §2.5，230K 打
平）；参考机同谱系（去审查）模型的另一次实测也是正常上升形状（1718→2399）。 - 不是配置：用与报告
作者机相同的 pw2 + auto:16384 组合、在同谱系模型上，参考机形状正常；报告作者机在自己的两套 arm
（16384 与 auto）上都出现倒挂（−12% / −20%）。 - 不是参考机的特例：参考机 prefill 随长度上升至
2.77K，与 2690v4 机同形，属正常规律。
3.5 同口径内存带宽对照（2026-10-15）
双方同一协议复测：原版 McCalpin STREAM v5.10、每数组 512 MiB、16 线程、OMP_PLACES=cores + 
OMP_PROC_BIND=spread、绑定经逐线程 CPU id 核对（报告作者机侧为其复核任务公开的 numactl 直跑结
果）：

参考机三轮独立运行波动 <0.3%、Solution Validates 通过。内存条结构少 8 倍（双通道 DDR5 vs 双路 8 通
道 DDR4）的参考机反而快约 6 倍；报告作者机的数值已低于单条 DDR4 通道的理论值（19.2 GB/s），不是
「内存档次」或「测法差异」可解释的量级，指向该机宿主内存通路的结构性故障。快速排查排序：① 宿主过
度分配/换页（guest vmstat 的 pswp、宿主 balloon/zram）；② 宿主背景争用（基准运行时在宿主侧采数 + 
numastat -p <qemu-pid>）；③ BIOS 内存交织/通道配置（Memory/Channel Interleaving、DIMM
Configured Speed）；④ 交叉 NUMA 与 vCPU 放置（单独最多 ÷2–3，不足以解释全部）。
候选原因（按证据强度）：
宿主内存数据通路异常（新晋第一嫌疑）：见 §3.5——其宿主内存实测约为参考机的 1/6，与 PCIe Gen3 x8
（~7 GB/s 量级）相近。prefill 的冷读+staging 需求随上下文增长，撞上该天花板即产生「越跑越掉」的形
状；若坐实为换页/争用，这也是该机一切「时快时慢」现象的候选总解释。

VM 直通的链路未复测：报告作者机自述「历史探测 ~9.5–10.2 GB/s，本轮未复测链路宽度」。部署指南原
文：prefill 由「显卡算力 × 链路带宽」决定；参考机实测同一引擎下 x8 较 x4 快约 +14%。
显存余量≈0：该机启动空余仅 497/511 MiB；上下文越长 KV 工作集越大，边缘抖动/驱逐会把「固定开销摊
薄（升）」翻转成「边际成本上涨（降）」。
长上下文 KV 走主机侧坏路径：长 prompt 下大部分 KV 在主机内存侧流式读取，经过 VM/链路延迟叠加的通
道，每 token 代价随深度上升。
复核清单（建议该机实测）：
nvidia-smi -q -d PCIE 当场记录两卡链路代际/宽度；跑一次固定内存的 host→device 带宽测试（对照
Gen3 x8 单卡 ~6.5–7 GB/s 量级）。
引擎日志三类检查：显存低余量告警、KV streaming 计数、stall 报告。
用同一模型 + 同一环境变量集合复跑 32K/128K/230K：形状若恢复上升，说明是模型/环境配置；若仍倒
挂，则坐实为该机数据通路。
宿主侧：VM 的 vCPU/IO 线程绑核是否与直通卡的 PCIe 根同 NUMA；大页设置；条件允许时做裸机对照。
4. 给两位网友的建议（按优先级）
三对齐再比：同任务（建议用计数类固定任务，接受率应回到 95%+）、同模型同量化（IQ3_S 对
IQ3_S）、同补丁与环境变量。
同任务重放：把同一批请求体分别打到两台机器（同一份 payload），用引擎日志口径出数——这是把「任
务/接受率」变量钉死的标准做法。
报告作者机执行上节复核清单四项。
2690v4 机：换 IQ3_S 复跑一轮，可直接验证「量化 ≈1.4×」的折算。
